## 1. Назначение

Math Page Vision Lab — учебное приложение для распознавания одной страницы математического учебника с помощью мультимодальной модели OpenAI. Пользователь загружает изображение или PDF, выбирает страницу PDF, запускает распознавание и изучает результат в форматах Markdown и JSON.

Главная учебная цель этой версии — пройти путь от локального проекта до публикации сайта на Vercel и связать Vercel с отдельным GitHub-репозиторием. Инструкция и интерфейс должны помогать новичку понять структуру приложения, переменные окружения, Git-коммиты и этапы публикации.

Приложение проектируется для публикации на Vercel. Архитектура, обработка запросов, загрузка файлов, переменные среды и локальная проверка должны соответствовать модели Vercel Functions и ограничениям платформы. Python используется для серверной функции обработки распознавания, а веб-интерфейс собирается как приложение, совместимое с Vercel. См. [Python Runtime](https://vercel.com/docs/functions/runtimes/python) и [ограничения Vercel Functions](https://vercel.com/docs/functions/limitations).

## 2. Цели и границы

### Цели

- Научиться создавать веб-проект, вести его в Git и подготовить отдельный репозиторий GitHub.
- Развернуть приложение на Vercel и описать подключение проекта к GitHub и настройку переменных окружения в Vercel.
- Распознавать одну страницу за один запрос к OpenAI Vision API.
- Показывать источник и извлечённые элементы в удобном интерфейсе.
- Формировать Markdown программно из проверенного JSON и позволять скачать оба результата.
- Сохранить небольшой и понятный для изучения код.

### Не входит в первую версию

- RAG, embeddings, векторные базы, пакетная обработка и очередь заданий.
- Аккаунты, авторизация пользователей, база данных и постоянное хранение документов.
- Облачное хранилище загруженных файлов.
- OCR отдельным движком, автоматическое исправление математики, оценка точности.
- Docker, Redis, Celery, фоновые задачи и отдельный постоянно работающий Python-сервер.
- Автоматическое создание GitHub-репозитория или отправка кода в удалённый репозиторий.

В первой версии сайт и endpoint распознавания доступны публично, без регистрации и общего кода курса. Посетителей нельзя надёжно отличить от участников курса. Перед публикацией настроить ограничение частоты вызовов endpoint в Vercel Firewall и принудительный лимит расходов отдельного проекта OpenAI; порядок настройки и проверки описать в README. Эти ограничения снижают риск расходов, но не подтверждают личность посетителя.

## 3. Архитектура и стек

Использовать монорепозиторий, который можно развернуть из корня проекта на Vercel:

| Область | Технология |
|---|---|
| Веб-интерфейс | Next.js, React, TypeScript |
| API | Python 3.12 Vercel Function, один HTTP endpoint для распознавания |
| Модель | OpenAI Python SDK, Responses API, структурированный вывод |
| Проверка данных | Pydantic |
| PDF | PyMuPDF; преобразовывать только выбранную страницу в изображение |
| Изображения | Pillow |
| Локальная конфигурация Python | `.venv` в корне, `requirements.txt`, `.python-version` |
| Хостинг | Vercel, импорт проекта из собственного GitHub-репозитория |

Сохранять код компактным и разделённым по ответственности. Предпочтительная структура:

```text
app/                 # страницы и компоненты интерфейса Next.js
api/                 # Python Functions Vercel
  recognize.py       # проверка загрузки, PDF/изображение, запрос к OpenAI
python/              # схемы и функции Python, используемые API
requirements.txt
.python-version
.env.example
.gitignore
README.md
```

Допускается скорректировать структуру для совместимости с текущим шаблоном Next.js/Vercel, сохранив простоту и Python-обработчик в отдельной функции. Не добавлять Streamlit в опубликованный интерфейс. Если локальная разработка требует запуска frontend и API раздельно, README должен содержать точные команды и пояснить роль каждого процесса.

Vercel Functions имеют ограничение тела запроса 4.5 MB. Поэтому принимать изображения и PDF размером не более 3 MB каждый; проверять размер в браузере и повторно на сервере. Не кодировать большие файлы в base64 без необходимости. При превышении лимита показывать понятное сообщение. Не подключать Blob или иное постоянное хранилище. Ограничения описаны в [документации Vercel о лимитах функций](https://vercel.com/docs/functions/limitations).

Python-функции Vercel имеют временную файловую систему: доступен только временный каталог `/tmp`; исходники и пользовательские загрузки не должны сохраняться постоянно. Для PDF создавать временные данные на время запроса и удалять их после обработки.

## 4. Пользовательский сценарий

1. Пользователь открывает опубликованную страницу приложения.
2. Выбирает JPG, JPEG, PNG или PDF размером до 3 MB либо нажимает отдельную кнопку «Тест», чтобы загрузить встроенный пример из `public/demo/page_005.jpg`.
3. Для PDF выбирает страницу (нумерация с 1).
4. Видит предварительный просмотр выбранной страницы.
5. Явно нажимает «Распознать страницу».
6. Сервер отправляет только выбранное изображение страницы в OpenAI API.
7. Приложение валидирует ответ по Pydantic-схеме и показывает результат.
8. Пользователь переключается между просмотром Markdown и JSON и скачивает `.md` или `.json`.

Повторное распознавание выполняется только по явному нажатию кнопки. Перерисовка страницы, смена вкладки или скачивание не должны повторять платный API-запрос. Результат держать в памяти текущей сессии браузера; после перезагрузки он может быть утрачен.

## 5. Входные файлы и обработка

- Поддерживать JPG, JPEG, PNG и PDF; проверять расширение, MIME-тип и возможность декодирования.
- Максимальный размер исходного файла — 3 MB. Ограничение одинаково применять в интерфейсе и API.
- Для изображения проверить корректность через Pillow и при необходимости привести к RGB без агрессивной обработки.
- Для PDF определить число страниц и разрешить выбрать одну страницу. Предпросмотр выбранной страницы выполнять в браузере через PDF.js; в Python Function передавать исходный PDF и номер страницы.
- На сервере преобразовывать через PyMuPDF только выбранную страницу. Начинать с 200 DPI, сохранять пропорции и ограничивать итоговое изображение 2560 пикселями по длинной стороне и 6 миллионами пикселей в целом. Преобразовывать в RGB и кодировать как JPEG с высоким качеством; если размер изображения слишком велик, постепенно снижать качество и затем разрешение. Не уменьшать страницу заранее до 2048 пикселей только из-за прежней модели `gpt-4.1-mini`: качество мелких формул проверить на образцах с `gpt-6-luna`.
- Не извлекать PDF-текст напрямую. Модели передавать только визуальное представление выбранной страницы.
- Обрабатывать повреждённые, зашифрованные и пустые PDF понятным сообщением.
- Ограничить число страниц PDF разумным значением (например, 100) и сообщить об ограничении заранее.
- Временные файлы создавать только в `/tmp` и удалять после обработки. Не логировать содержимое, ключи и исходные документы.

## 6. Распознавание и схема результата

Использовать актуальный OpenAI Python SDK и Responses API. По умолчанию использовать OpenAI; предусмотреть `OPENAI_BASE_URL`, чтобы пользователь мог указать другой сервис, совместимый с Responses API, изображениями и структурированным выводом. Модель по умолчанию — `gpt-6-luna`; имя модели считывать из `OPENAI_MODEL`. Не переключать модель автоматически, если указанная модель недоступна. Интерфейс может показывать выбранное имя модели и базовый адрес API, но никогда не ключ. Возможность работы с изображениями и Structured Outputs подтверждена [документацией модели](https://developers.openai.com/api/docs/models/gpt-6-luna).

Один запуск распознавания должен делать один основной запрос к Vision API. В запрос включить выбранное изображение и инструкцию: точно извлекать видимое, сохранять язык и порядок чтения, не решать задачи, не добавлять и не исправлять содержание; сомнительные фрагменты отмечать как неразборчивые. Использовать Structured Outputs/JSON Schema, если выбранная модель это поддерживает, и валидировать результат через Pydantic.

Типы элементов: `heading`, `paragraph`, `definition`, `theorem`, `rule`, `formula`, `example`, `problem`, `solution`, `answer`, `table`, `figure`, `other`.

Минимальная схема ответа:

```json
{
  "document": {
    "filename": "math_page.jpg",
    "page_number": 1,
    "language": "ru"
  },
  "elements": [
    {
      "id": "element_001",
      "order": 1,
      "type": "heading",
      "text": "Квадратные уравнения",
      "latex": null,
      "description": null,
      "rows": null,
      "has_header": null
    }
  ]
}
```

Поля: `document` содержит имя файла, номер страницы и язык; `elements` — упорядоченный список с уникальным `id`, номером `order`, `type`, распознанным `text`, формулой `latex` без `$`, описанием `description` и ячейками таблицы `rows`. Для `table` поле `rows` содержит непустой массив строк, каждая строка — массив текстовых ячеек; число ячеек во всех строках одинаково. Поле `has_header` показывает, является ли первая строка заголовком. Для остальных типов `rows` и `has_header` равны `null`. Неприменимые поля допускают `null`. Дополнительно проверять, что список непустой, все `id` уникальны, а `order` начинается с 1 и идёт без пропусков. Для имени файла и номера страницы использовать сведения из выбранной пользователем загрузки, а не полагаться на догадку модели. Не вводить координаты, confidence scores и сложные связи между элементами.

Markdown формировать кодом из валидированного JSON, не делать дополнительный LLM-запрос. Формулы в JSON хранить без разделителей; в Markdown использовать `$...$` для встроенных и `$$...$$` для отдельной формулы. Таблицы строить из `rows`: при `has_header=true` использовать первую строку как заголовок Markdown-таблицы; при `false` добавить пустой технический заголовок, сохранив все распознанные строки как данные.

## 7. Интерфейс

- Русский язык, краткие подписи и пошаговые подсказки для начинающего.
- Отдельно объяснить, что изображение страницы будет отправлено OpenAI для распознавания и что API-запрос может тарифицироваться провайдером.
- До загрузки показывать допустимые типы и максимальный размер.
- Предоставить отдельную кнопку «Тест», загружающую встроенный пример из `public/demo/page_005.jpg` в тот же предпросмотр. Нажатие «Тест» не должно вызывать OpenAI API; запрос выполняется только после явного нажатия «Распознать страницу».
- Указать, что встроенный файл в каталоге `public/` является общедоступным ресурсом сайта. Не использовать для него личные или конфиденциальные документы.
- Для PDF показывать количество страниц, выбор страницы и её предпросмотр.
- Во время распознавания показывать состояние запроса и блокировать повторное нажатие.
- После успеха показывать предпросмотр страницы и вкладки/переключатель «Результат», «Markdown», «JSON».
- Предоставлять скачивание Markdown и JSON с безопасным именем файла.
- Если API возвращает расход токенов, показывать входные, выходные и общие токены; не вычислять стоимость без надёжных данных о тарифе.
- При смене файла или номера страницы очищать устаревший результат и ошибку, чтобы распознавание не относилось к прежнему источнику.
- Не показывать ключ API или диагностические трассировки в браузере.
- Ключ OpenAI хранить только в серверных переменных среды Vercel. Никогда не использовать префикс `NEXT_PUBLIC_` для секретов.

## 8. Ошибки и безопасность

Показывать понятные сообщения для неверного формата, слишком большого файла, повреждённого/защищённого PDF, отсутствующего ключа, ошибки авторизации, недоступной модели, лимита API, сетевой ошибки и невалидного JSON. Не показывать пользователю stack trace, секреты или необработанный ответ провайдера.

Обрабатывать загруженные данные в памяти или временном каталоге только на время запроса. Передавать внешнему сервису только одну выбранную страницу. Не сохранять документы и результаты на сервере после запроса и не вести журнал содержимого. В README объяснить, что выбранная страница отправляется OpenAI и обрабатывается по условиям провайдера.

Уточнить, что развернутая ранее авторизация с Nginx и SQLite не входит в Vercel-версию и что в MVP нет учётных записей.

Инструкции должны быть пригодны для человека, впервые публикующего учебное приложение. Отдельно указывать, какие действия выполняет Codex локально и какие пользователь выполняет в интерфейсах GitHub/Vercel.

## 15. Ожидаемый результат

Codex должен подготовить работающий исходный код приложения, файлы зависимостей и конфигурации, `.env.example`, `.gitignore`, README, локальные Git-коммиты и отчёт с результатами. Реализовать основной сценарий, не оставлять заглушку распознавания. Удалённый репозиторий и deployment не создавать автоматически; дать пользователю точные дальнейшие шаги.

**Главный критерий успеха:** пользователь может локально запустить приложение, загрузить одну страницу, получить структурированный результат, а затем следуя README связать собственный GitHub-репозиторий с Vercel и опубликовать приложение.
